> 来源:模块一窗口的全面审计 + 整合人核验。本文档**只描述问题与修复建议,不含已执行的修复**。
> 每条标注:现象 / 根因 / 建议修复 / 优先级 / 建议归属。执行前请在 #18 对齐归属。

## 问题 1|P1 · 4 条条件子监控成为孤儿

- **现象**:23553159(30 分钟开局量>5)、23553160(30 分钟剧情推进<1)、23553161(30 分钟战斗开始≥5)、23553162(30 分钟战斗结算<1)四条监控,描述均为「复合告警的条件子监控」。全 org 搜不到任何 composite 监控——这 4 条的消费者(composite)不存在,且它们按子监控设计**不带通知对象**,现在既不告警也没人消费。
- **根因**:composite monitor 在本 org 创建实测 400(query invalid,全 org 无 composite 先例)——两条断流监控改写为比率形态后,4 条条件子监控未清理。
- **建议修复**(三选一):
  1. 删除 4 条子监控(比率监控已覆盖其语义,且新增"进度腰斩"捕获);
  2. 补建 composite(不推荐:org 实测 400,不可用);
  3. 给 4 条补通知对象使其成为独立监控(不推荐:与比率监控语义重叠,会双告警)。
- **推荐:方案 1**。

## 问题 2|P2 · 经营监控只有 2/3 条,第 3 条"未创建"

- **现象**:经营模块只有拒付率与阿策降级率两条;第 3 条找不到。
- **根因**:**这是设计,不是失败**。第 3 条是「支付转化异常」(payment-conversion),定义存在于 `business-observability.json` 的 `pending_baselines` 段——按模块三窗口的设计,**等真实充值流量积累 1-2 周基线后再创建**,脚本有意跳过 pending 项(离线校验输出"Pending baseline (not deployed): payment-conversion, economy-inflation"可证)。
- **建议**:无需修复。触发创建的条件:preview 上有人真实走完充值流程并积累基线后,把 `pending_baselines` 里的阈值从占位改为实测值,再执行 apply。
- **前置依赖**:见问题 4(充值流程已走通——funnel 已上报,只是 charge 指标在 US5 缺失,根因见该条)。

## 问题 3|P1 · 「原地接管」未生效,拒付率与阿策降级监控重复

- **现象**:比率/业务版两条监控(拒付率 23553166、阿策降级 23553167)描述写"原有告警原地接管",但旧副本 23526678(拒付率)、23526682(阿策降级)仍在 US5——两套同时生效,告警会重复通知。
- **根因**:US5 上存在**两批监控**:①基础观测副本 10 条(2026-11-04 前后由 QQ 账号迁入,含拒付率/阿策降级);②业务版 9 条(2026-11-05 由登录态部署)。"原地接管"在设计里依赖脚本识别同名旧监控并 PUT 更新,但**旧副本与新版名称不同**(旧:`[小猫回家记] 支付拒付率过高(演示业务异常)`,新:同名但查询形态不同)或脚本按名称匹配时旧副本已在(需逐条核对——实际结果是新建而非更新)。
- **建议修复**:保留**业务版**(带 `business-module` 标签、查询已适配),删除**旧基础副本中的两条重复项**:
  - 23526678(旧拒付率)
  - 23526682(旧阿策降级)
- **归属**:观测负责人。⚠️ 删除前确认这两条当前状态(拒付率此前因本机 e2e 数据处于 Alert,删除前先看是否有未处理的告警上下文)。

## 问题 4|P1 · kitty.payment.charge 在 preview 从未上报(根因已修正,2026-11-05 晚)

- (原判断:preview 上还没人走过充值流程)——**已被数据推翻**:充值流程确实走通了——
  `kitty.payment.funnel`(模块三新埋点)在 preview 正常上报:charge_attempt 3 次、charge_success 1 次;
  前端 RUM 也记到 10 次 recharge_entry_click。
- **矛盾实锤(本地实验)**:本地起 game + 假 DogStatsD 监听器,走一次充值(success+declined 双路径),
  UDP 捕获显示 **kitty.payment.charge 与 kitty.payment.funnel 同时发出**——代码层 charge 埋点完全正常。
- **矛盾保留在中间层**:preview 上同一函数相邻两行的两个指标,funnel 到了 US5,charge 没到——
  问题锁定在 **Datadog Agent(US5 的接收层)或 intake**。两个候选解释:
  1. org custom metrics 额度/新指标拒收(班级共享 org 全员上报,额度满时新指标被 intake 拒收);
  2. Agent 的 DogStatsD 拒收(tag 数/长度/解析)——查 Agent 日志与 DogStatsD 状态段:
     kubectl -n cn-haozhe-wang exec <agent-pod> -- agent status(需要 namespace 权限,找浩哲)。
- **监控的务实修正(立即可做)**:kitty.payment.charge 短期内不可依赖——两条支付监控的查询
  改用有数据的 funnel 指标:拒付率 = funnel{step:charge_declined} / funnel{step:charge_attempt};
  支付错误条挂起等 charge 指标恢复;待指标恢复后再切回 charge 形态(信息更全)。
- **归属**:Agent 日志排查需要 namespace 权限(浩哲);intake 层排查需要 org 管理员(老师)。
