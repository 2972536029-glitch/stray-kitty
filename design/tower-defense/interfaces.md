# 难度、奖励与模块接口

更新：2026-10-25｜L00 保留序章规则；L01 新增第一章首领战与正式补给结算。

序章取用源仍为 `38545c3b9b93698b3a2cbbc23608c51e192388cc`。本轮扩展既有 Go 服务和单进程 JSON 存档，接入开战预留、有效耗用、未用返还与分档奖励；不再使用独立试玩的 localStorage 仓库。家园完整仓库界面仍由 UI 同学继续制作，本轮提供第一章的最小出战补给选择入口。实现与实际验证以项目接入记录为准，不用验收清单代替运行结果。

## 1. 流程与职责

`preparation / home / explore → START_BATTLE → battle → COMPLETE_BATTLE → settlement → CONTINUE` 沿用团队主流程。服务端 `activeBattle` 提供场次身份，前端不创建替代场次。

| 模块 | 当前职责 |
| --- | --- |
| 战斗／闫琦雯 | L00 与 L01 局内玩法、六猫援军、地图规格、补给规则、首领、有效耗用；承接战斗补给库存与结算扩展 |
| 主流程／公共框架 | 原有阶段、会话、命令串行、存档与公共接口；战斗宿主按 stageId 挂载模块 |
| 事件 | 判断开战档位，保存到场次快照；战斗不重新评分 |
| 家园／UI | 仓库入口、库存展示、装配选择及反馈；本轮小型准备卡提供可运行的接入口，不代替完整仓库界面 |
| 服务与存档 | 在现有 Go/JSON 架构内校验持有数量、预留、返还、发奖和请求去重；数据库迁移与正式运维仍待认领 |
| 剧情 | 长期角色身份与入队时点继续由剧情方维护；L01 六猫是本关援军，不写入长期伙伴表 |

L00 `alley_rescue` 为 3×7／10 波。L01 `alley_boss` 为 5 行×12 列包围框内的凸形小巷／8 波，关联已有章节 `alley`；包围框不是完整可走矩形，合法地格、障碍和路线以 L01 配置为准。只有完成 `alley_rescued` 后才能进入 L01。

失败均为 `lost → settlement → CONTINUE → preparation`，准备页由 `lastResult.stageId` 识别要重试的关卡；不是失败回探索。L01 胜利继续后回家园，不触发 L00 的点点救援剧情。L00 原有剧情、家具、邮票和材料首通奖励保留。

## 2. 开战与锁定清单

公共契约见 [TypeScript 类型](../../web/src/contracts/index.ts) 与 [OpenAPI](../../docs/openapi.json)，服务实现见 [battle.go](../../server/internal/service/battle.go)。

```ts
{ type: 'START_BATTLE', stageId: 'alley_boss',
  supplies: { 'warm-can': 2, 'bouncy-treat': 1 } }
```

`supplies` 可省略，表示空清单。只接受两个已知物品键的非负整数，不接受 null、字符串、小数、未知键或超过拥有量；不把 food、material 自动换成道具。

| 项目 | L00 | L01 |
| --- | --- | --- |
| 免费基础份额 | 暖罐 2、冻干 1 | 无 |
| 仓库预留上限 | 额外暖罐 2、冻干 1 | 暖罐 4、冻干 2，总量 6 |
| 模块输入 | `extraSupplies` 来自 `activeBattle.supplies ?? {}` | 完整 `loadout` 来自同一预留快照 |
| 局内重整 | 达突破上限后免费本波重整 | 3 次突破判失败，没有序章免费重整 |

服务在同一事务内从可用 `GameState.inventory` 扣出预留数量，保存到 `activeBattle.supplies`。战中清单固定，标题暂停不释放预留。进行中的场次不能用 `START_STORY`、`GO_EXPLORE` 等命令绕过结算或建立另一场。重复开局请求使用原幂等键返回原回执，不二次预留。

## 3. 结果、耗用与奖励

```ts
{ type: 'COMPLETE_BATTLE', attemptId, outcome: 'won',
  usedSupplies: { 'warm-can': 1, 'bouncy-treat': 0 },
  report: { leaks: 0, bossDefeated: true } }
```

`usedSupplies` 是本次最终有效的自带物品耗用，不是整个背包余量，也不是累计点击数。服务拒绝负数、未知键、超过预留的用量。L01 必须提供 `usedSupplies`（允许 `{}`）和完整 `report`；胜利要求 `bossDefeated=true` 且 `leaks<3`。L00 没有预留的旧场次可继续只提交 `attemptId + won/lost`；存在预留时必须提供有效耗用。

本轮战斗模拟仍在客户端。服务检查报告形状、场次和资源合法性，并执行存档事务；没有服务端重演整场战斗，不宣称已经具备权威战斗验证或反作弊能力。

结算一次性完成：返还 `预留−有效耗用`，按胜负与原场次档位处理奖励，保存通关标识、场次终态与回执。只有整个写入成功才返回“已保存”。失败不发胜利补给；已使用的自带份额仍消耗，未用份额返还。免费教学份额从不退入仓库。

| 奖励 | 当前规则 |
| --- | --- |
| 每次新的胜利 | 简单／普通／困难基础 2／3／4 份 |
| 每关第一次胜利 | 额外 2 份，使用 `completedStages` 跨难度去重 |
| L01 零漏怪胜利 | 每次额外 1 份；战斗猫受伤、治疗、休整不影响 |
| 每份类型 | 暖罐 70%、冻干 30%，服务端抽取 |
| 重复请求 | 原幂等键返回原结果；新键重复提交已终结场次被拒绝，不重发 |

L00 与 L01 都已接分档补给，L00 不附加零漏奖励。旧存档已经完成的关卡不追补新首胜奖励，下一次有效胜利可获得常规奖励。补给与原剧情首通奖励分开统计。`lastResult.battleRewards` 返回 `supplies`、`baseCount`、`firstClearBonus`、`perfectBonus`、`difficulty`；只有收到服务端确认后，界面显示本次入库物资。

## 4. 难度接入与恢复

主流程／宿主将 `activeBattle.modifiers.shadowPressure` 的 −1／0／1 转为 `low / medium / high`，缺省普通、非法值拒绝。只读开战时保存的快照，不读取最新事件结果重新评分，也不在三档倍率之外叠加旧压力倍率。L00 实战敌人和 L01 小怪／Boss 都只按三档调整体力 0.8／1／1.2；路线、数量、攻击、速度不随档位暗改。

`lost` 后保留待用修正，重试新建 attempt 并沿用难度；`won` 后清空 pending 修正，没有新事件时下一场普通。同场恢复与失败后新场次分开处理。

返回标题保留并暂停当前 DOM／战斗实例，继续冒险恢复现场。整页刷新恢复同一服务场次、档位和预留清单，但局内从 ready 重开；L00 重新教学，L01 重置本场棋盘、波次、体力和有效耗用。本轮不逐帧保存，也不在每次用物品时持久化消耗；未结算的旧战况与耗用一起回退，预留不会再扣一次。结算请求已经发出但响应未知时，沿用 HttpGameApi 保存的原请求与幂等键重试，不重新开始战斗。

L00 教学结束恢复 initialInventory，本波重整恢复波初快照，使用替换而非叠加；有效自带耗用同步回退。L01 无免费初始物资，不继承 L00 的重整补给机制。L01 玩家确认「撤离本场」后，通过既有 COMPLETE_BATTLE 提交 lost 与有效耗用，返还未用自带物资、不发胜利奖励，继续后回 preparation；未另增 HTTP 放弃命令。返回标题仍只是暂停，直接关闭页面也不等同于已结算撤离。

## 5. 生命周期和协作边界

每个战斗视图自行管理唯一 RAF、页面隐藏暂停、订阅和卸载清理；宿主传入全局暂停、标题页、遮罩和 busy/pending 条件，不叠第二个 tick。终态只通知一次，结果网络失败沿用原命令恢复。局内暂停保护、技能与物品规则见 [补给与奖励](items.md) 和关卡配置。

后续第二至第五章遵循每关一名固定 Boss、同档随章节变强的设计方向；这些关卡尚未在本轮创建。橘猫军需官、进阶物品、正式招募和任意阵容选择、完整家园仓库 UI、数据库迁移与多实例存储不在已完成范围内。

## 6. 联调验收

服务测试覆盖库存不足、非法清单、预留持久化、刷新读取、失败返还、原事件快照、三档首胜／重复胜利、零漏加奖、奖励抽取边界、事务失败回滚、重复请求与 HTTP 数据校验。浏览器与引擎实测应分别记录，不能将服务测试的模拟结果当作真实通关，也不能将旧独立试玩回执测试当作主项目验证。
